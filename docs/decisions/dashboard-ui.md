# Dashboard and publication controls

Astro renders the searchable library rows, publication filters, account controls, and review forms. React hydrates only the title and row menus. Their props contain labels and links, with optional icons and groups for presentation. The library uses `ArtifactSummary.createdAt` and a generic document icon because summaries contain no edited date or content format.

The dashboard uses the shadcn Base UI [button registry source](https://ui.shadcn.com/r/styles/base-nova/button.json) and [dropdown menu registry source](https://ui.shadcn.com/r/styles/base-nova/dropdown-menu.json), retrieved on 2026-10-12. Local copies remove unused variants, submenu controls, and selection controls. The source license remains in `apps/dashboard/src/components/ui/LICENSE`. Base UI owns menu focus, keyboard navigation, and positioning. Tailwind uses the dashboard's [Catppuccin Mocha blue tokens](catppuccin-blue.md) and its two self-hosted fonts, without remote fonts or icon packages.

The exact dependency override keeps `@vitejs/plugin-react` at 6.1.1. `@astrojs/react` 7.0.1 declares `oxc-transform-react` ^0.145.0, and plugin 6.1.1 accepts that range. Plugin 6.1.2 requires ^0.152.0. The override prevents an incompatible peer resolution while preserving the integration's declared dependency range.

Astro's built-in `security.csp` generates script hashes in server responses. It retains the panel's existing restrictions and denies script attributes. Middleware remains the fallback for responses without a policy. The preview policy remains independent. The publication separates its trusted header from the revision-bound content response as described in the [Catppuccin design decision](catppuccin-blue.md).

The publication Worker retains its own CSS and native title, Information, and Files disclosures. It loads no dashboard assets or React runtime. Its header stays within 45% of the viewport, leaving at least 55% for the sandboxed document.

Revision selection stays in native GET forms. Publication uses the existing four-field `PublishCommand` and native POST form. Menus do not mutate artifacts. The retained verifier opens the selected export menu and native viewer disclosures before checking the same revision identifiers, archive bytes, attachment bytes, and isolation headers.

## Read mode

The owner moves between artifacts in `/read`, a two-column panel page inside the shell: a 388px list on the left, the selected artifact's pane filling the right. A publication portal was rejected because the publication Worker authorizes one artifact per cookie and serves no scripts. The panel already holds the owner session and the preview route, so read mode adds no contract, REST, MCP, or Worker change.

The page reads the same `panel.library` page as the library. The `artifact` parameter selects a card by ID. When it names an artifact outside the page, such as a shared link to the second page, `panel.artifact` supplies its head revision and title. Without it the first row is selected, or the last row when `at=last`. Filter, search, and page links drop the selection, like the cursor, so the list and preview stay in agreement.

The list starts with the status pills and the project chips, one scrolling line each. Its rows are 55px: the title and the update time, then the state, the revision, and the kind. In the whole library they group by project like the library table, and `group=none` from the library turns grouping off. The selected row has the `--accent-a1` surface and the 3px indicator.

The pane header shows the title, the state, the revision, the update time, and the slug, then the position, Anterior and Siguiente, Compartir, Detalle, Abrir publicación when the artifact has a publication, Publicar rev. N when it has pending changes, and fullscreen. The position is `offset + index + 1 de counts[status]`. `counts` covers the same scope and search as the list, so the total stays honest under filters, search, and sort. The `offset` parameter travels only with a cursor, on the dashboard's own page links, including the library's. A missing offset, one that is not a multiple of the page size, or one that disagrees with the counts hides the position instead of guessing, and so does a selection from another page. Index follows the order the rows are shown in, grouping included.

Anterior and Siguiente are links to the neighboring rows. On the last row Siguiente opens the next page through the cursor. The model has no backward cursor, so on the first row Anterior can reach only the first page, which needs none: from the second page it opens the first page with `at=last`, and from the third page on it is disabled. A disabled control is an `a` with `aria-disabled` and no `href`, so it takes no focus. Publicar posts the existing publication form with a `return` path. After a confirmed publication the route redirects to that local path, so the reader returns to the same artifact without the button. Other outcomes keep the result page. Fullscreen calls `requestFullscreen` on the frame from the panel, as the detail preview does, so it needs no CSP change and no new sandbox token. It shows only with JavaScript.

Each row and each pane link is a GET link, so read mode works without JavaScript. The server also renders every row's pane into a `template`. A bundled script, hashed by `security.csp`, swaps in that template on a click, on a pane link to a row of the page, or on `j` and `k`, pushes the row URL, and restores the selection on `popstate`. The pane after a client-side move is therefore the pane a link would load. `j` and `k` follow Siguiente and Anterior, so at a page edge they load the adjacent page. The arrow keys move focus through the list and stop at its ends. The swap replaces the iframe rather than setting its `src`, because a frame navigation adds a history entry and Back would walk the frame instead of the reader URLs. The preview keeps the detail page's sandbox: `markdownPreviewSandbox` for Markdown and `allow-scripts` otherwise. The rail's Modo lectura link opens read mode in the current project or Sin proyecto scope. The reader's project chips, the same component as the library's, switch project without leaving read mode.

At 760px and below the list stacks above the pane and scrolls inside 40% of the viewport height. The pane header wraps under the title, Compartir and Detalle keep only their icons and accessible names, and the controls grow to 40px. The prototype has no phone reader, so this keeps the desktop order and every control within reach without horizontal scrolling.

## Shell

Every signed-in page shares one shell from `layouts/Panel.astro`: a navigation rail, a top bar, and a status bar around the page content. The shell reads only what the layout already receives, `workspace`, `location`, and `identity`.

The rail is a 56px `nav` landmark named Principal on `--bg-chrome`. It holds the brand mark, then Biblioteca, Proyectos, and Modo lectura, and at the bottom the theme toggle, Conectar herramientas, and the account avatar. Each item is an icon with an accessible name and a title. The current destination has the `--accent-a2` surface, the accent color, and the 3px indicator. An artifact, a project, Sin proyecto, and a task page mark Biblioteca as the current section. Conectar herramientas and Mi cuenta are native `details` elements that open anchored panels, so they open, close, log out, and close all sessions without JavaScript. With JavaScript, Escape and an outside click close them, and opening one closes the other. Any `[data-open-tools]` link opens `#connect-tools`.

The project list left the chrome. Projects stay reachable from the Proyectos page and the project chips in the library and in read mode, and a nested page's breadcrumb links back to its project.

The top bar is 52px. Biblioteca and Proyectos put their title in the bar as the page's `h1`. Read mode puts a back link to the library, the `Ruta` trail, and its `h1` in the bar. A project, Sin proyecto, an artifact, and a task page show the `Ruta` breadcrumb instead and keep their own `h1` in the content. The search on the right stays a native GET form whose icon is its submit button. A page can add actions to the bar through the `bar` slot, as the library does with Modo lectura.

The status bar is 30px on `--bg-chrome`. It shows the workspace totals: artifacts, published, and with pending changes. Read mode replaces them with the size of the list it reads, such as Leyendo 26 artefactos. A page fills the shortcut slot on its right through the `status` slot and lists only shortcuts that work on it, as read mode does with `j` and `k` and the library does with Esc, which closes its menus and the rail panels.

At desktop widths the rail, the top bar, and the status bar are fixed to the viewport, and the content column pads itself clear of them. The document stays the scroller instead of an inner region, so keyboard scrolling, the skip link, anchor links, browser find, printing, and zoom behave as on any page. `scroll-padding` keeps anchors, find matches, and focused content clear of the bars. The bars are fixed rather than sticky because a sticky bar is part of the scrolled document, so focusing the account avatar, which sits inside the bottom scroll padding, scrolled the page by 26px. Read mode fixes its column to the viewport height and scrolls its list and preview inside. Printing hides the rail, the status bar, and the search.

At 760px and below, which includes 1440px at 200% zoom, the rail becomes a fixed 56px bottom bar with the same items and its indicator on the top edge. The brand mark and spacer drop out. The tools and account panels open as sheets above the bar. The top bar scrolls with the page and wraps the search to its own row, and the status bar keeps the totals and drops the shortcut hints. A bottom bar keeps every destination one tap away without taking width from a 390px screen, and only it stays on screen while the page scrolls.

`tests/panel-theme.browser.proof.ts` measures the rail, the top bar, the status bar, and the open panels in both themes at 1440 and 390.

## Library

One filter bar replaces the four stats cards, the old status tabs, and the project dropdown. It holds the status tabs with their counts, a divider, a chip for each project in `workspace.projects` order and for Sin proyecto, each with its tone dot and count, and on the right the grouping menu, the sort menu, and the view toggle. Every control is a GET link, and the two menus are native `details` elements, so the bar works without JavaScript. The workspace totals the cards showed now live in the status bar and the Sin proyecto chip. With a project or Sin proyecto selected, an extra chip returns to all projects. At desktop widths the chips wrap inside their column so every project stays visible. At 760px and below the tabs and the chips each become one row that scrolls sideways inside the page, which keeps the table near the top of a phone screen. The guest who has only shared artifacts sees a short note that links to Conectar herramientas, since the rail panel is not a link.

The table rows are 38px tall. The title carries the slug in mono beside it, or the description when there is no slug. Columns are state, type, revision, and updated, and the column headers still sort on the server. In the whole library the rows of the current page group under a header per project, in `workspace.projects` order and then Sin proyecto. Grouping is presentational over the page's 25 cards, so the header count is the number of rows in that group on this page, and it says `en esta página` whenever the list has more than one page. `group=none` turns grouping off and brings back the project column. Like `view`, it is a dashboard-only parameter that every filter, sort, page, and search link carries, and read mode drops it. A project or Sin proyecto page is one group, so it shows no header. The cards view does not group.

When the scope has pending changes, a banner sits above the table. A second `panel.library` call filtered to `status: 'pending'` in the same scope, without the search, supplies its artifact, the most recently updated one. It names the head and published revisions, links Comparar to the detail page's compare tab, and posts Publicar through the same `PublicationForm` the detail page uses. With more than one pending artifact it links to the pending filter with the count.

Each row ends with Leer, Compartir, and the existing menu. On a device with hover they appear on row hover, on keyboard focus inside the row, while the row is selected, and while its menu is open. A device without hover shows them always. At 720px and below the row collapses to two lines and keeps only the menu button, so one tap reaches every action, including Modo lectura. Without JavaScript the menu island is hidden and a native `details` with the same links, Eliminar included, takes its place. A selected or keyboard-focused row shows the 3px side indicator and no glow.
